# 用户集中反馈修复计划（2026-09-15）

状态：方案建立，尚未开始本轮代码施工。  
范围：视频播放器、采集卡、PS5 串流、增强管线、视频导出和颜色管理。  
本计划不授权发布新版本、不替换运行组件、不修改显卡驱动。

## 1. 目标与原则

本轮目标是把用户反馈拆成可复现、可定位、可回归的工程任务。每项修复必须同时具备：

- 现象对应的日志或测试证据；
- 明确的状态、队列、时间戳和颜色契约；
- 可独立回归的自动测试或手工验收步骤；
- 失败时保留真实错误码，不用“回退成功”掩盖后端失败；
- 不把一台显卡、一个采集卡或一次成功启动当作全设备兼容证明。

播放器、采集卡和串流继续共享 `FrameSource -> EnhanceGraph -> FrameSink`。本轮不复制第二套增强链，也不通过无限队列或阻塞 UI 来掩盖性能问题。

## 2. 当前已知证据

### 已有证据

- 采集音频自动同步和启动积压已有独立修复候选；其测试使用合成采集时序和真实 WASAPI 静音输出，仍需反馈用户的真实采集卡复测。
- 现有串流异常日志中，视频已收到、D3D12VA 已解码，NVOF、SR、FG 初始化均返回成功；随后出现 `swapchain mode rejected requested=3 actual=4`，会话被取消。当前更像显示交换链模式回退处理错误，不能直接归咎于配对或网络。
- OBS 捕获兼容模式和窗口 resize 已有历史修复文档，但 1.2.0 后仍需用 1.1.0 对照确认是否回归。
- HDR/SDR 和 HDR10/5.1 已有颜色合同和施工记录，但用户反馈“都发灰”，必须增加端到端灰阶和色块证据。

### 尚未证明

- Dolby Vision 原生解码、RPU 保留和原生输出；不能用 HDR10 代称 Dolby Vision。
- RTX 4060/4070/4070 Ti 的真实过载边界；不能用 RTX 5070 或 RTX 50 代替 40 系验收。
- 用户导出日志中 `completed sample queue overflow` 与 BT.2020 错误的完整上下文；需要原始导出日志和输入媒体信息。
- “PS5 VRR 导致音频数秒延迟”的因果关系；需同一采集卡 VRR 开/关对照。

## 3. 分阶段施工顺序

### 阶段 A：不可用状态与恢复

优先修复会让用户无法继续使用的错误状态。

#### A1. PS5 串流增强初始化失败

现象：配对成功、收到视频，但点击增强后显示初始化失败或会话被关闭。

实施：

1. 将交换链能力探测、请求模式和实际生效模式分开记录。
2. SDR、HDR、直播兼容和窗口 resize 使用明确的回退顺序；实际模式改变时重新绑定呈现资源，不直接终止串流。
3. 把状态拆成“传输连接、视频解码、增强初始化、呈现初始化、运行中”五层。
4. NGX/NVOF/XeSS 失败只禁用对应后端，基础视频仍可显示。
5. 为每个阶段记录 HRESULT、NGX/XeSS 返回值、交换链格式、色彩空间和窗口尺寸。

验收：配对成功后无增强、NR、SR、DLSS FG、XeSS FG、HDR/SDR、全屏/窗口各启动一次；任何单项失败都不能关闭基础视频。

#### A2. OBS resize 回归

现象：1.2.0 起使用 OBS 游戏采集，放大缩小窗口后进入错误状态；1.1.0 无此问题。

实施：统一 resize 生命周期：暂停提交，等待旧资源 fence，重建交换链和尺寸相关纹理，原子 reset SR/NR/FG/flow/depth，再恢复提交。禁止旧 backbuffer 在 GPU 使用期间被释放或复用。

验收：连续拖动窗口、最大化/还原、全屏切换、DPI 改变、OBS 同时捕获；检查无黑帧、无错误状态、无旧尺寸资源访问。

#### A3. 采集卡断开自动重连

实施：检测 DirectShow/WASAPI 设备失效、样本停止、端点错误和设备路径变化；进入 `reconnecting`，保留 UI/设置，暂停历史，按递增间隔重试原设备；成功后重新建视频格式、音频时钟和增强历史。多次失败后才进入可重试错误。

验收：拔线/插回、设备被 OBS 占用、设备格式改变、音频端点单独断开、连续断开重连；不切到其他设备，不丢失用户选择。

#### A4. 采集卡选择记忆

实施：以稳定 `DevicePath` 为主键，显示名仅作展示；保存视频格式、帧率、像素格式和音频端点。启动时优先匹配上次设备，设备不存在时显示未连接，不静默选别的设备。

验收：重启软件、拔插设备、同名设备并存、设备顺序改变、旧配置升级；配置文件不得保存临时枚举序号作为唯一标识。

### 阶段 B：颜色与输入格式

#### B1. HDR/SDR 发灰

实施：每帧或每源显式记录 `matrix/range/transfer/format`，统一进入 linear working color；SDR 不走 HDR tone mapping，HDR 根据显示器能力选择 HDR 输出或明确 tone map 到 SDR；禁止重复转换。

验收素材：SDR 黑白灰阶、BT.709 色块、BT.2020/PQ、HLG、full/limited range。验收日志必须能解释输入、工作空间和输出，不以截图肉眼作为唯一证据。

#### B2. 视频导出 BT.2020 转换失败

实施：导出前按颜色合同分流 SDR 与 HDR。SDR 使用 BT.601/709 SDR 转换；HDR 使用 BT.2020 PQ/HLG 到 HDR10，或在用户选择 SDR 时执行明确 tone map。遇到不支持的组合要在导出前报错，不能进入错误转换函数。

验收：导出输出帧数、PTS、颜色元数据和解码回验一致；HDR 输入不得触发 `BT.2020 input is not supported by BT.601/709 SDR conversion`。

#### B3. Dolby Vision

分三层交付：

1. 识别 Profile、基础层和 RPU 是否存在；
2. 先提供基础层兼容播放，或明确转换为 HDR10/SDR；
3. 只有确认 RPU 解码、编码器、Windows 显示链和授权后，才评估原生 Dolby Vision 输出。

完成前 UI 必须标明“兼容播放/转换”，不得宣称原生 Dolby Vision。

### 阶段 C：播放器交互和流畅性

#### C1. Seek、全屏进度和快捷键

实施：拖动过程中只更新目标位置，松开后执行一次精确 seek；新 seek 覆盖旧 seek。解码 worker 异步处理，UI 立即显示目标位置。全屏保留进度条、鼠标唤醒和键盘焦点；左右方向键默认前后10秒。

验收：4K 文件连续拖动、拖到末尾、反复前后跳、全屏/窗口切换、音频恢复；不出现先弹回旧位置再跳转的视觉回弹。

#### C2. 播放器流畅性

先测量再优化：记录解码等待、增强等待、GPU fence、呈现 deadline、UI 消息延迟、队列长度和丢弃原因。消除 UI 等待解码、每帧 CPU fence wait、旧 seek 结果提交和无界任务队列。

实时预览可以丢弃过期增强工作，但不能把导出路径改成丢帧，也不能放慢音频制造同步假象。

#### C3. UI 闪烁

排查 Win32 无效区域、交换链重建清屏、DPI resize 和控件重建。改为差异更新控件，画面层与 UI 层分离，交换链重建期间保留上一帧或明确的加载状态。

验收：模式切换、全屏、resize、错误提示、滚动和参数实时修改截图回归；检查无黑屏闪烁和控件跳动。

### 阶段 D：内部处理分辨率和性能

#### D1. NR 内部处理分辨率

增加 `480p / 720p / 900p / 1080p / 1440p` 挡位。它们表示 NR/增强工作尺寸，不改变最终输出尺寸；按源宽高比计算实际 extent，显示源/内部/输出三组分辨率。

每档记录显存、GPU 时间、实际处理 FPS 和丢帧；默认仍保持现有设置兼容，不擅自替换用户已保存的设置。

#### D2. 40 系过载

先区分真实 GPU 超时、队列积压、显存不足和错误阈值。记录每阶段 GPU 时间、显存预算/占用、队列深度、后端和驱动版本。持续过载时按预设降级内部处理分辨率或关闭单个高成本效果，不能直接把目标帧率锁30并伪装成正常。

验收至少覆盖 RTX 4060、4070、4070 Ti；本机没有对应实卡时只做代码和日志验证，不宣称硬件通过。

#### D3. FG/XeSS 计时与冗余

统一 GPU timestamp/fence 接口，分开显示 GPU 执行、CPU 提交、等待和呈现时间。后端不提供硬件时间戳时显示“未提供”，不能把0或未知参与总延迟。审计 NR、SR、光流、FG 是否重复等待或重复计入总延迟。

#### D4. FG 后端失败

按不可用、驱动不足、分辨率不支持、资源不足、初始化失败、运行时 Evaluate 失败分类。UI显示后端和真实错误码；失败只禁用该后端并保留基础播放，不能静默回滚成“已开启”。

### 阶段 E：视频导出队列

#### E1. completed sample queue overflow

导出路径使用独立有界队列和背压；接近上限时暂停生产或等待可复用 slot，不允许无限堆积。`flow=0 fallback=single-image` 只允许在首帧、seek、场景切换等无历史阶段，并在导出报告中统计。

验收：导出长视频、4K、FG 开关、场景切换和 HDR；检查队列峰值、最终归零、帧数、PTS 连续性、取消清理和输出可解码。

## 4. 依赖关系与交付批次

### 批次 1：A1、A2、A3

目标：不再因串流初始化、窗口变化或采集卡断开进入不可恢复状态。

### 批次 2：B1、B2、C1

目标：先统一颜色，再修 seek/全屏交互；否则后续性能对比没有可信画面和时间线。

### 批次 3：A4、C2、C3、D1

目标：改善重复操作、低配置可用性和日常流畅度。

### 批次 4：D2、D3、D4、E1

目标：处理后端失败、40系过载、计时不完整和导出队列问题。

### 批次 5：B3

目标：在兼容播放和 HDR 转换稳定后再评估 Dolby Vision，不把未验证的原生输出塞进主线。

## 5. 每批次固定验收合同

- 构建成功，记录实际构建命令和依赖路径；
- 相关单元/集成测试通过，失败日志保留；
- 至少一个真实 GUI 短测；
- 记录输入、工作、输出分辨率与颜色合同；
- GPU/NGX/XeSS/NVOF 返回值和 HRESULT 进入日志；
- 不将运行组件、SDK、模型、用户配置或测试媒体提交源码 Git；
- 未接用户硬件时明确写“未执行”，不拿合成测试冒充实卡验收；
- 本轮不自动发布版本，发布需要另行明确授权。

## 6. 当前需要的外部证据

施工前优先收集：

1. 用户提供的完整“串流异常.log”；
2. 视频导出失败的完整日志、输入文件信息和导出设置；
3. 4070/4070 Ti 过载日志，包含驱动版本、源分辨率、内部处理分辨率和所有效果开关；
4. HDR/SDR 发灰各一份源媒体或采集卡颜色日志；
5. OBS resize 回归的1.1.0与1.2.0日志；
6. 采集卡断连、重新插入和设备枚举日志。

在这些证据到齐前，可以先施工 A4、C1、C3 和日志/状态框架；不能声称已经解决用户设备上的 B1、D2、E1 或 A1。

## 7. 明确不做的事情

- 不通过增加缓冲解决卡顿；这会把卡顿变成更高延迟。
- 不用“系统 HDR 没开”解释所有发灰现象；必须先核对颜色合同。
- 不把 HDR10、HLG 或基础层播放宣称为 Dolby Vision。
- 不把一台 RTX 50 的结果推广到 RTX 40 全系列。
- 不用0、未知或软件提交时间伪造 XeSS/FG GPU 耗时。
- 不把导出队列溢出、flow fallback 和颜色转换错误合并成一个笼统的“性能不足”。
